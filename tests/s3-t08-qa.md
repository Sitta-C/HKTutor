# S3-T08 reminder QA

Historical evidence below predates the payment lifecycle fix. Its unpaid class-reminder counts
describe the old contract; current policy sends unpaid students payment reminders only and enables
class reminders after payment. The runnable verifiers follow the updated
[recipient and QR prompt contract](../apps/api/README.md#class-and-payment-reminders-s3-t05).

Executed on 2026-11-03 (Asia/Bangkok), from `2027e95` on `test/s3-t08-reminder-qa`.
Source: [Sprint 3 Backlog, row 9](https://docs.google.com/spreadsheets/d/17RMTjXa26ho7blv-TK5pbJFbHxVHJEBRPKCXk9x5AE0/edit?gid=504754817#gid=504754817).
The baseline includes S3-T05, S3-T06 and S3-T07. This change extends tests and the existing verifier;
runtime behavior, DTOs, wire types and schema are unchanged.

## Environment

- Windows, Node 24.19.0, pnpm 11.19.0, Playwright Chromium.
- New container `hktutor-s3-t08-reminders-20261103`, cached PostgreSQL 16 Alpine, UTC,
  loopback port 55449, database `hktutor_s3_t08_test`. All 24 migrations applied without seeding.
- The verifier refuses remote URLs, missing opt-in, URL options, unsafe database names and any
  database already containing bookings. Only synthetic fixtures were written and removed in `finally`.
- Reminder eligibility uses injected UTC instants in 2099, separated by three days to isolate scans.
  The cron unit test uses Jest's fixed clock. No sleep advances reminder eligibility. Concurrency
  tests hold a real booking lock and observe both workers waiting through `pg_stat_activity` before
  committing the competing change; a deadline only guards a failed test.
- Browser tests intercept API traffic. They verify UI behavior against synthetic server responses;
  PostgreSQL assertions independently verify real persistence and locking.

## Evidence

The [captured PostgreSQL evidence table](#postgresql-evidence-table) records actual booking and
slot IDs, fake now/start UTC, Bangkok display, expected recipients/key suffixes, counts and exact
database assertions. Each key expands to
`reminder:<bookingId>:<slotId>:<startAtUtcISO>:<band>:<kind>`, uniquely paired with `userId`.
Expected keys are constructed independently from the production helper.

| Requirement                                    | Assertion                                                                                                                                                                                                                                                                                    |
| ---------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 24h +/-1ms, 1h +/-1ms, 0 +/-1ms, more than 24h | Fresh paid and unpaid bookings for every delta; exact scan/write counts and persisted recipient/key pairs. Midnight starts also check Bangkok date rollover.                                                                                                                                 |
| Paid and unpaid recipients                     | Unpaid: student class + payment, tutor class; paid: student and tutor class only, in either band. Persisted event types match their key suffixes.                                                                                                                                            |
| Excluded statuses                              | PENDING, COMPLETED, CANCELED and EXPIRED each produce zero rows at 2h and 30m.                                                                                                                                                                                                               |
| Catch-up and restart                           | First run at 2h writes three 24H rows; a new worker at 30m adds only three 1H rows. A separate booking first seen at 30m gets only 1H.                                                                                                                                                       |
| No after-start event                           | Fresh runs at start and 1ms after start produce zero rows; existing rows and first read receipts remain byte-for-byte unchanged by repeated and after-start ticks.                                                                                                                           |
| Idempotency and both recipients                | Two independent Prisma clients wait on one booking lock: combined result is two scans, three creates, three duplicates, zero failures. Exact stored pairs prove both recipients survive the shared class key.                                                                                |
| Reschedule and committed state                 | Payment/cancel/reschedule commits after the scan and before the job obtains the lock suppress stale payment/old-slot writes. Two notified occurrences in the same 1H band produce six distinct recipient/key pairs; repeating the new occurrence creates none.                               |
| Failure and retry                              | An AFTER INSERT trigger fails on the payment row after the class rows were attempted. Zero rows for either recipient survive that booking; a healthy neighbor retains all three. Removing the trigger and retrying creates exactly three missing rows. Logs contain only error class/counts. |
| Real inbox persistence                         | NotificationsService reads the job-written rows: four student reminders and two tutor class reminders across both bands. Mark-one changes the unread count by one; repeats and restart preserve the first receipt and every stored row.                                                      |
| Translated browser behavior                    | Both languages and both roles retain translated titles/details, booking links, Bangkok timestamps, unread/read badges and expansion without implicit acknowledgement.                                                                                                                        |
| Stale payment history                          | Both languages open an old payment reminder into current unpaid, paid, pending, completed, canceled, expired or missing booking state. Only confirmed + unpaid exposes an enabled Create test QR button; following history never writes a payment.                                           |
